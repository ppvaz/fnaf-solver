**The numbers below do not move when only this file changes**, and that is

rows are the ones where a mechanic can hide.

## 2026-08-26, second pass: nine clusters run down

The first pass of the day took the unread list from 87 to 37. This pass reads
nine of the remaining clusters end to end. One is a **real gap**, one is a
one-frame constant the engine has wrong, five are inert or already implemented,
and two are dead code that only looks alive.

Everything below was read with `readdump.py object 3 "<name>"` first and
`group` second, because the trap this repository keeps falling into is that a
*partial* read of a shared object looks exactly like a contradiction. Three of
the fourteen groups writing Foxy's `AlterableValue3` nearly got filed as an
engine defect earlier today; the same shape recurs here twice (`blackout` v3 and
`new bonnie` v8 both look like live mechanics until you find that nobody reads
them).

### Vocabulary this pass had to pin down first

Four dump encodings that every verdict below depends on, none of which were
written down anywhere in the repository:

- **`ot=-1,num=24,loader=GlobalCommon,value=5` is the frame-delta scalar**, the
  `min(4, frameDelta/16.666)` that `SOURCE-DUMP-GUIDE.md` §8 attributes to group
  1236. Read it as `dt`. Every `x = x + 1 * dt` in the sheet is "one 60 fps
  frame per frame", so a threshold like `>= 300` really is 300 frames = 5 s.
- **`C ot=-3 num=-1` is Start of Frame** (confirmed by g486-487, which
  `config.js` already cites as the `your view` parking rule) and
  **`C ot=-1 num=-7` is Fusion's "only one action when event loops"** — a
  once-per-continuous-true-period trigger, not a per-frame condition. Several
  groups below are harmless *only* because of that flag.
- **Group folders are real and two of them are switched off.** A `RESTRICT 32`
  event whose condition renders `38:Group:Group: N` is a folder header; the
  `FLAGS 8192` events after it are its children, and a `NUM -11` child closes
  it. `FLAGS 16384` on a header means the folder is **disabled in the editor**:
  in frame 3 that is Group 44 (g908, empty) and Groups 48-67 and 99-105 —
  56 groups in total. None of the 37 unread state/input groups is inside one.
- **Folders can also be switched at run time, and the dumper will not tell you
  which.** `A ot=-1 num=6` / `num=7` with a `39:GroupPointer` parameter is
  activate/deactivate, and CTFAK renders the parameter as the *class name*, not
  the target index. Frame 3 does this in eleven places at once in **g0**
  (Start of Frame, gated on global value 8, which nothing in the whole dump ever
  writes — so it is injected by the runtime, almost certainly a platform flag).
  **Consequence: no claim of the form "group X never runs, its folder is off"
  is verifiable from this dump.** Every verdict below therefore rests on group
  *order* and on who reads a value, never on folder state.

### Cluster 1 — `blackout`, g514-519 / g723-726 / g845: **A REAL GAP** (plus two inert halves)

The `blackout` object (handle 131) is the office-encounter sequencer, and it
carries four independent counters that had never been separated:

| Slot | What it is | Groups |
| --- | --- | --- |
| v0 | the 300-frame office sequence counter | g514 `+dt` while `in danger == 1`, g516 clamps at 0, g535/g537 consume it, g536 zeroes it |
| v1 | the black overlay's **flicker duty cycle** | g517 `Random(50)` for `20 < v0 < 100`, g518 `Random(50)+20` for `100 <= v0 < 200`, g519 `100` at `v0 >= 200`; g520/g521 hide/show on `v1 < 25` |
| v2 | the **fade-out counter after the sequence ends** | g534 sets it to 1 on the `in danger` edge, g535 `+dt` once `v0 >= 300`, g536 resets everything at `v2 >= 250`, **g845 jumps it straight to 250** |
| v3 | nothing | g723 clamps, g724 drains and shows, g726 zeroes on `viewing > 0` |

**v1 is presentation** — the ramp from "no overlay" to 50% flicker to 90% to
solid is exactly the visible blackout, and nothing but g520/g521 reads it.

**v3 is dead code.** g724 drains it and shows the overlay while it is positive,
so it looks like a second, independent blackout. It is not: a scan of every
action in frame 3 finds **no group anywhere that ever sets `blackout` v3 to a
positive value** — the only three writers are the three groups in this cluster,
and all three only ever write 0 or `v3 - dt`. v3 is 0 for the whole night, so
g724 never fires and g725's hide runs exactly once, at night start, because of
the "only one action when event loops" flag. Verdict: **inert**, and it is the
clearest example in the sheet of why "who writes this" has to be asked before
"what does this do".

**v2 is the gap.** The engine ends a blackout the instant the 300-frame counter
expires (`src/engine.js:456`, `this.blackout = {active:false,...}` at
`f >= this.blackout.until`, with `BLACKOUT_FRAMES = s(5)` in `src/config.js:45`).
The source does not. After g537 raises `check and move` at `v0 >= 300` and
g538-555 resolve the occupant and drop `in danger` to 0, **`v0` stays at 300** —
nothing decrements it — while g535 counts `v2` from 1 up to 250. Only then does
g536 zero `v0`, `v1` and `v2` together. And `v0 > 0` is a live gameplay gate:
**g436 requires `blackout` v0 == 0 before Toy Bonnie may roll his office overlay
`Active 19`, and g438 requires it before Toy Chica's `chicalookatyou` may be
created.** Those two overlays are what set `in danger` in the first place
(g443/g444). So the real rule is:

> After an office encounter resolves, Toy Bonnie and Toy Chica are locked out of
> starting the *next* one for a further **249 frames (~4.15 s)** while the
> blackout fades. The engine gives them no lockout at all — a new encounter can
> begin on the frame after the old one ends. The source's true encounter-to-
> encounter floor for these two is ~549 frames (~9.2 s), not 300 (~5 s).
>
> **And the player can throw that grace away.** g845 fires the first time
> `viewing > 0` while `v2 > 0`, and sets `v2 = 250` — so the very next tick g536
> zeroes `v0` and the lockout ends early. It cannot fire *during* the encounter,
> because g254/g257 refuse a monitor raise while `in danger != 0` and g911
> forces `viewing = 0` whenever the mask is fully on; it fires on the first
> raise *after* the resolution. A pilot that snaps the camera up the moment a
> blackout clears is choosing the harsher branch, and paying up to 4.15 s of
> free time for it.

What it would change: the two `openingRule: 'mask'` characters (`toybonnie`,
`toychica` in `src/config.js:544-545`) would get a post-encounter cooldown, and
the cooldown would become a function of when the pilot next raises the monitor.
That is a policy lever the simulator currently cannot express. It is **not** a
Night 6 headline — the mutex four and W. Foxy are unaffected, since g436/g438 are
the only gameplay readers of `v0` — but it is the first sourced rule found that
*rewards* leaving the monitor down after a blackout, and the vent-camp routes in
`docs/strategy/` are built around monitor cadence.

Not yet done, and deliberately: the engine change is not made here, because
`src/` belongs to another session in this working tree. This paragraph is the
record.

### Cluster 2 — `drop everything`, g614-619: **implemented, but it names the live input path**

g613/g617 are two folder headers around the same button. Group 32 (g614-615)
reads `ot=-6 num=-4`, "user clicks on object" — the mouse. Group 33 (g618-619)
reads `ot=46 num=-88` on `Multiple Touch` with touch id 5 — the phone. Both write
the same thing:

- monitor up (`flip panel button` v0 == 2), no flip in progress (v1 == 0), mask
  off → `drop everything = 1`;
- mask fully on (v0 == 2), no flip in progress, `viewing == 0`, **`in danger == 0`**
  → `drop everything = 1`.

`drop everything` itself is already implemented (`src/engine.js:95` cites
g718-721/g624; g262 and g274 execute it). So the button is **redundant with the
monitor and mask buttons the engine already models** — one press just routes into
the same forcedown. Verdict: **implemented/redundant.**

Two facts fall out that are worth keeping anyway:

- **The drop button cannot take the mask off during an office encounter**
  (`in danger == 0`). The monitor arm has no such condition.
- **g258 is the release for `flip panel button` v1, and it lives only in the
  touch folder.** g258's condition is `NOT (touch 5 over drop button)` and its
  action is `v1 = 0`. Every press group (g254/g257 monitor, g267/g270 mask,
  g614/g615/g618/g619 drop) refuses while `v1 == 1`, and g276/g279 hide the
  monitor bar and mask button while it is set. So v1 is (a) a one-tick input
  lock after a *forced* flip — g262 and g274 set it after g258 has already run,
  so it survives into the next tick — and (b) the **hold-debounce for the drop
  button**: while the finger stays on it nothing clears v1, so it cannot repeat.
  A normal monitor press sets v1 in g257 and has it cleared by g258 four groups
  later, in the same tick, so it locks nothing.

  Group 23 (the mouse monitor press, g254) has no equivalent of g258. A build
  driven by the mouse folder alone would latch v1 on the first press and never
  release it. That is independent evidence that **the `Multiple Touch` folders
  are the live Android path and the mouse folders are the dead PC path** — which
  matters when citing an input group: cite the touch one.

### Cluster 3 — g1-9, the monitor/mask animation state machine: **implemented**

g1, g6, g9 and g10 are the four animation-completion latches, and g1015-g1022
are what feed them: on the tick an animation Active starts (`C -29`) its v0 is
zeroed, and every tick after that v0 grows by `dt`. So v0 is a tick count and
the thresholds are frame counts:

| Group | Threshold | `src/config.js` | Agrees? |
| --- | --- | --- | --- |
| g1 `mmonitorUp` | `>= 12` → `flip panel button` v0 = 2, `blip` | `MONITOR_ANIM_UP = 12` (:426) | yes |
| g6 `mmonitorDown` | `>= 22` → hide; g7 then clears v0 | `MONITOR_ANIM_DOWN = 22` (:427) | yes |
| g9 `mmaskOn` | `>= 12` → `mask` v0 = 2 | `MASK_ANIM_ON = 12` (:428) | yes |
| g10 `mmaskOff` | `>= 14` → hide; g11 then clears `mask` v0 | `MASK_ANIM_OFF = 15` (:429) | **no — off by one** |

**The engine's `MASK_ANIM_OFF = 15` is wrong; the sheet says 14.** The reason is
visible in the constant's own comment: the block is `[SOURCED]` from the
*animation bank* (`mmaskOff 11fr@speed75` → `11*100/(75*60) = 0.2444 s`
→ 14.67 frames) and 14.67 was rounded up. The other three round to their event
thresholds exactly; this one does not, and the event threshold is what actually
flips the state. One frame is 16.7 ms — small, but the device plans time the
mask→monitor seam to 180 ms, so it is the wrong sign of error to leave in.
Not changed here (`src/` is another session's).

g2/g3/g4 restore the camera on a completed raise: `viewing = last viewed` if
there is one, else CAM 09 on nights 1-6 and CAM 07 on night 7. `last viewed` is
written by g263 (every 200 ms while `viewing > 0`). `src/config.js:451-454`
already cites g2-4 and g486-487 for exactly this, with `initialCamera` and
`parkedCamera`. Implemented, and the two agree.

The one thing g1-9 adds that is not written down: **g7 and g11 gate the
"animation finished, go to state 0" step on `being attacked by == 0`.** During a
jumpscare the monitor and mask states freeze rather than resetting. Cosmetic —
the run is over — but it explains why a death frame can photograph a half-raised
mask.

### Cluster 4 — `new bonnie` v8, g901-902: **inert (vestigial)**

g901 zeroes Toy Bonnie's `AlterableValue8` while he is at marker 122; g902 sets
it to 1 if he is there with the cameras down. **Nothing reads it** — not as a
`-27` condition anywhere in frame 3, and not as an `ot=2,num=16,oi=99,value=8`
expression either.

Read on its own this looks like an unmodelled Toy Bonnie timer, and it is worth
saying why it is not, because the neighbouring groups are the same shape and

Verdict: **inert.**

### Cluster 5 — `your view`, g482-485 / g812 / g827-828: **inert (presentation), with one observable worth having**

`your view` (handle 126) is the marker naming the displayed camera, and its v1 is
a **camera-static countdown in frames**, not a game state:

- Set to `20 + Random(100)` by g468-477 when a character whose `C`
  (`AlterableValue2`) is still above zero is standing on the viewed camera;
  set to `50 + Random(100)` by g366/g368/g419 when Toy Bonnie, Toy Chica or Toy
  Freddy is mid-hop (`A == 2`) on it; set to 5 by g827/g828 (**night 7 only**,
  cams 8 and 9).
- Drained by **g482** (`Max(0, v1 - dt)`), and consumed by **g483** (one `blip`
  per burst) and by g448, g478-481, g508-512, g522, g604, g606 — all of which
  `coverage.py` already classes as presentation.

So the cluster is **inert** for the simulator. But it is not inert for a device
pilot, and it corrects a sentence already in this file: the earlier `g458-477`
write-up says the `C` counter is "bookkeeping, not a mechanic" because "nothing
anywhere gates on `C` except the Puppet's branch in g406/407". **g468-477 gate on
it too.** The consequence is a free observable: *a static burst plus a blip on
the camera you just opened means someone with a fresh movement token is standing
on it.* `C` is set to 10 on acceptance and drained a frame at a time, so the
window is roughly ten frames wide and the burst it triggers lasts 20-119 frames.
Nothing in `tools/device` looks for this today.

**g484/g485 are inert outright**: they mirror monitor-up into `your view` v21
(`0` when `viewing == 0`, `1` otherwise) and **nothing ever reads v21**.

**g812 is dead code.** It reads `blackout timer >= 30` and would set
`your view` v1 = 200 (a ~3.3 s static), clear `random image`, and play sample
`'m'` — visibly the "camera goes to a distorted image" effect. It cannot fire.
`blackout timer` (handle 169) is incremented by `+dt` in exactly three places —
g114 (CAM 05, flashlight on, neither Toy Chica nor W. Bonnie there,
`random image == 3`), g159 (CAM 08) and g167 (CAM 11, Puppet at stage 3) — and
then **g842/g843/g844, which run afterwards and between them cover the entire
domain, overwrite it every single tick**: 1 if `blackout` v0 > 0, 1 if
`blackout` v2 > 0, 0 otherwise. The counter is therefore clamped to {0, 1} at the
end of every frame and can never reach 30. Two features share one counter and
the later one wins. Verdict: **inert**, by group order.

### Cluster 6 — `sockpuppet` v3, g493: **inert**

g493 is `Always → sockpuppet.v3 = v3 + dt`, i.e. a free-running frame counter,
and g494/g495/g496 zero it whenever the Puppet advances or resets a stage. It
looks exactly like "time since the Puppet last moved". **No condition and no
expression in frame 3 ever reads `sockpuppet` v3.** The Puppet's actual stage
state is v18 (0-3, consumed by g167 and g494-496) and its route uses v0/v1/v2.
Verdict: **inert** — a dead timer, most likely the remains of an earlier design.

### Cluster 7 — g329, the home positions: **implemented**

g329 is a single Start-of-Frame event that parks all eleven characters:
W. Bonnie, W. Chica, W. Freddy and W. Foxy on **cam 8** (Parts/Service); Toy
Bonnie, Toy Chica and Toy Freddy on **cam 9** (Show Stage); Balloon Boy on
**cam 10**; the Puppet on **cam 11**; Mangle on **cam 12**; Paper Pals on
**cam 4**. Every one of those is the first element of the corresponding `path`
in `src/config.js:540-547` (`withfreddy` `[8, …]`, `toyfreddy` `[9, …]`,
`mangle` `[12, 11, …]`, and so on), with the Puppet and Paper Pals handled
outside that table as the comment at `src/config.js:535-538` says. The two agree.

### Cluster 8 — g910, `flip panel button` v1 at frame start: **inert**

`Start of Frame → flip panel button v1 = 1`. Because g910 sits after g258, the
lock survives into tick 2 and is released by g258 on tick 3 — a two-tick input
freeze at the very start of the night, before the player can plausibly press
anything. Its real function is covered in cluster 2. Verdict: **inert.**

### Cluster 9 — g916 and g1040: **inert in a clean install, but g916 is a device precondition**

**g916 is the `unlimitedPower` cheat.** Its condition is "global value 2 == 1"
and its action is `battery life = <battery life's maximum>`, every frame. Global
value 2 is written in exactly two places in the whole dump: frame 0
(`01-Initialize & Setup`) g69/g70, which load it as
`Max(0, Min(1, GetIni("freddy2", "cheats", "unlimitedPower")))`, and frame 27
(`28-Unlocks`) g227, which toggles it from the `unlimitedPowerSwitch.Active`
control. The same screen carries **`fastNights`** (global 3) and **`radarMap`**
(global 4). Verdict: **inert in normal play** — a clean save has it at 0, or the
flashlight would not drain at all.

It is recorded here anyway because two of those three cheats silently invalidate
this project's device measurements if the phone has them on:

- **`unlimitedPower` (global 2, g916)** — the flashlight budget stops existing.
  Every "192 frames of headroom" figure in `CLAUDE.md` would be unmeasurable.
- **`fastNights` (global 3, g627/g628)** — this is the night clock itself. g627
  advances the `AM` counter once per **1000 ms** when the cheat is off; g628
  advances it once per **500 ms** when it is on; g629/g630 turn 70 of those into
  one in-game hour. So an hour is 70 s normally and **35 s with the cheat**, and
  a night is 420 s or 210 s. `src/config.js:26-27` has `NIGHT_FRAMES = s(420)`
  and `HOUR_FRAMES = s(70)`, i.e. the engine is the cheat-off branch and is
  correct — but a device run on a phone with `fastNights` set would clear a
  "night" in half the time and every graded interval would be half of what the
  engine expects.
- `radarMap` (global 4) reaches frame 3 at g1104, which activates two folders at
  Start of Frame; the folder indices are not recoverable (see the vocabulary
  note above), so what it draws is `UNKNOWN(GroupPointer targets not rendered)`.

**Actionable and not done here:** nothing in `tools/device` checks the phone's
`freddy2` INI before a run. That is a one-line read of the game's saved settings
and it is the cheapest possible control on every battery and every wall-clock
number this project has taken off the device. Left as an open item because
`tools/` belongs to another session in this tree.

**g1040/g1041 are Golden Freddy's office figure fading out.** g776 (mask fully
on), g777 (monitor raise started) and g778 (hall light) all set the same internal
flag on `yellowbear`; g1040 fires while that flag is set, grows v1 toward 255 at
`<rate> * dt`, and writes v1 into the object's semi-transparency; g1041 destroys
the object at `v1 >= 255`. The gameplay-relevant half is the destruction, not the
fade: **g336's respawn roll requires the `yellowbear` instance count to be zero**,
so a mask-cleared Golden Freddy blocks his own re-spawn until the fade finishes.
The engine does model the flag (`this.gf.present = false` on a mask, at
`src/engine.js:284`, and the respawn roll at `:919` requires `!this.gf.present`),
so the shape is right; only the fade's *duration* would be new, and the dumper
flattens its rate to an unparsed `DoubleExp`. Verdict: **implemented in shape,
duration `UNKNOWN(DoubleExp rate not rendered by the dumper)`** — worth a line in
`EventTextDumper.cs` if anyone wants the number.

### What this pass could not determine

- **The `radarMap` folders (g1104) and g0's eleven activations.** CTFAK renders a
  `GroupPointer` parameter as its class name, so the target folder index is not
  in the dump. Fixing that is a change to `packages/source/decompile/EventTextDumper.cs`.
- **`yellowbear`'s fade rate (g1040)** — same cause, an unrendered `DoubleExp`.
- **Which global value 8 is** (g0's gate). Nothing in the dump writes it, so it
  comes from the runtime; "platform is mobile" is the obvious reading but it is a
  guess and is labelled as one.
- **The exact scoping of g2/g3/g4 and g7/g11.** They carry `FLAGS 32768` and sit
  between ordinary events, and the flag's meaning is not pinned. Their semantics
  are recoverable without it — unconditional evaluation of g2 would leave
  `viewing` permanently nonzero, and of g7 would make the monitor impossible to
  raise, so both must be scoped to the animation-completion event above them —
  but the flag itself is `UNKNOWN(event flag 0x8000 not decoded)`.

### Two notes for the tooling, from this pass

- **`grep` needs `-a` on the dump.** `SOURCE-DUMP-GUIDE.md` §9 warns that `awk`
  truncates at the NUL bytes and says `grep` is fine. It is *correct*, but it
  treats the file as binary and prints nothing at all — `grep -c 'num=82'`
  returns 0 on a file that contains it. Use `grep -a`, or read it in Python.
- **The counts in the two blocks at the top of this file cannot move when this
  file is the one that changes.** `coverage.py` deliberately excludes
  `docs/android/ANDROID-GROUP-MAP.md` from `cited_groups()` — "counting it would
  make the coverage map cite itself and erase every blind spot" — so writing a
  cluster up *here* leaves it in the unread list. That is why `g782-786`, run
  down earlier today, is still listed above. The blocks were regenerated at the
  end of this pass and are byte-identical to the ones already there: **37 unread,
  89% state, 86% input.** For these nine clusters to leave the list, their group
  numbers have to land in a page `coverage.py` does read —
  `ANDROID-SOURCE-STATUS.md` is the right one, and this session did not have
  write access to it.
